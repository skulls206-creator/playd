Prompt: Add an offline audio editor to my existing local music player

You are updating an existing browser-based music player that already:

Runs as a PWA and works offline (or mostly offline).

Loads and plays audio files from a local folder on the user’s machine (no server).

Extend this app with an “Audio Edit Mode” panel that lets the user edit any track offline using Web Audio and then save the edited version back to disk.

High-level goal
Add a simple but useful offline audio editor inside the app with these capabilities:

Visual waveform timeline for the current track.

Select a region of the audio to trim (set start and end).

Apply fade in / fade out on the selected region or whole clip.

Normalize volume for the clip (basic peak normalization is enough).

Export/save the edited clip back to the user’s local file system (either overwrite or “Save as new file”).

Use the Web Audio API (and optionally a small library like WaveSurfer.js for waveform display if that simplifies things).

Integration into the existing player
Add an “Edit” entry point:

In the UI where a track is shown (now playing area or track list), add a clear button: “Edit audio”.

Clicking “Edit audio” should:

Pause playback in the normal player.

Open an “Editor” view or panel for that specific audio file.

Editor layout:

Inside the editor view, create a layout like this:

Top bar:

Track name, duration.

Buttons: “Play/Stop in editor”, “Revert to original (discard edits)”, “Save”, “Save as new file”, “Back to player”.

Main area:

Waveform visualization with a draggable selection (start and end handles).

Time ruler (seconds) if possible.

Right or bottom control panel:

Numeric inputs/sliders for start time and end time of the selection.

Toggle/apply buttons for: “Trim to selection”, “Apply fade in”, “Apply fade out”, “Normalize volume”.

Audio processing requirements
Use Web Audio APIs and/or related utilities to actually modify the audio data:

Loading and decoding

For the selected track:

Re-use the existing Blob/File or fetch it via File System Access API (whatever the player currently uses).

Decode it into an AudioBuffer via AudioContext.decodeAudioData.

Keep the AudioBuffer in memory as the “current working buffer” for editing.

Trimming

When the user adjusts the selection (start/end):

Convert selection times (in seconds) to sample indices based on buffer.sampleRate.

To “Trim to selection”, create a new AudioBuffer that contains only the samples between those indices, copying channel data accordingly.

Replace the working buffer with this trimmed buffer, and update the waveform and duration.

Fade in / fade out

Implement fade in:

Over a specified time range at the start of the clip (e.g., first N seconds or selected region), multiply the samples by a ramp from 0 → 1.

Implement fade out:

Over a specified time range at the end of the clip (or selected region), multiply samples by a ramp from 1 → 0.

Apply these directly on the AudioBuffer channel data arrays so the changes are “baked in”.

Normalize volume

Implement simple peak normalization:

Scan all samples in the working buffer (all channels) to find the maximum absolute amplitude.

Compute a gain factor so that this peak reaches a safe target (e.g., 0.9).

Multiply all samples by that gain factor, clamping if necessary.

Preview playback inside the editor

Add a play/stop button that plays from the working buffer (including edits) using an AudioBufferSourceNode connected to the main AudioContext destination.

Support starting playback from a specific cursor or from the selection start if that’s simple to implement.

Waveform rendering

Option 1 (library): Use WaveSurfer.js or a similar library to display the waveform and visualize selection.

Option 2 (vanilla):

Downsample the buffer to a manageable number of points and draw min/max amplitudes on a <canvas> as a waveform.

Allow click-and-drag on the canvas to set the selection range.

Export / write-back to local file
The editor must be able to write the changed audio back to the user’s local storage:

Use OfflineAudioContext (or similar) to render the edited AudioBuffer to an output buffer or encoded audio.

Encode the result as an appropriate audio format (e.g., WAV via manual encoding in JS is acceptable).

If the app already uses the File System Access API:

For “Save”: write back to the original file via createWritable() → write() → close() on the file handle.

For “Save as new file”: prompt the user with showSaveFilePicker() and write the new file there.

If File System Access isn’t available, fall back to creating a downloadable Blob so the user can manually save the edited file.

UX details
Make it clear when the user is in “Edit mode” vs normal player mode.

Show some non-destructive behavior:

Keep an in-memory copy of the original buffer so the user can click “Revert to original” before saving.

Ensure edits are not accidentally lost:

Warn the user if they try to leave edit mode with unsaved changes.

Editor must work offline; no external APIs or remote processing.

Implementation notes for the AI
Keep the code modular, for example:

audioEditor.js for editor state and operations (trim, fade, normalize).

waveformView.js for drawing and interaction.

Integrations in the existing player UI code to open/close the editor.

Add concise comments around Web Audio, OfflineAudioContext, trimming, and saving so I can tweak logic later.

After you implement this, I should be able to:

Open the existing player.

Pick a local folder of audio files (current behavior).

Choose a track and click “Edit audio”.

See the waveform, select a region, trim, apply fade in/out, normalize.

Preview the edited audio.

Save the edited version back to a local file (overwrite or new file).

Return to the main player and play the edited file.
